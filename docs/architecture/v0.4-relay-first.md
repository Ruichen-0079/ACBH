# ACBH v0.4 Hobby Edition: relay-first architecture

Status: implementation contract for `rewrite/v0.4-relay-first-clean`
Base: PR #25 (`81c5e886f11fb973cb0f22a0b7fc7ed754529cfa`)

## Product boundary

ACBH v0.4 is a long-running Minecraft hosting agent with a stable public FRP
data plane and a small loopback-only control UI. Players connect to the VPS
public Minecraft port. The Coordinator is a control plane; it never forwards
Minecraft traffic and a Coordinator restart must not stop an established FRP
tunnel.

This iteration includes managed `frpc`, Minecraft lifecycle checks, component
state, a local HTTP API, an embedded web UI, structured events, diagnostics,
and recovery tests. It deliberately excludes host election, automatic
takeover, archive synchronization, P2P, multi-tenancy, Tauri/Electron, a custom
player relay protocol, PostgreSQL, mTLS, and automatic updates.

## Runtime topology

```text
players ---> VPS:25565 ---> frps:7000 <==== FRP data plane ====> frpc
                                                                  |
                                                                  v
                                                        localhost:25565
                                                              Minecraft

                       HTTPS control plane
acbh-agent ----------------------------------------------> Coordinator:6121
    |
    +-- RelayManager owns one managed frpc process
    +-- Minecraft manager owns one server process
    +-- 127.0.0.1:6130 serves the local API and embedded UI
```

The Agent is the lifetime owner. Closing a browser has no effect on Minecraft
or `frpc`. The RelayManager continues reconciling the desired state while the
Coordinator is temporarily unavailable.

## Component state model

Every component snapshot contains `state`, `updated_at`, an observation time
(`observed_at` or `last_ok_at`), `reason_code`, `user_message`, and an optional
`technical_message`. Transitions are emitted as structured events and retained
in a bounded in-memory ring.

| Component | States |
| --- | --- |
| Overall | `OFFLINE`, `CONNECTING`, `ONLINE`, `RECONNECTING`, `DEGRADED`, `STOPPING`, `ERROR` |
| Minecraft | `STOPPED`, `STARTING`, `READY`, `STOPPING`, `ERROR` |
| Relay | `OFFLINE`, `CONNECTING`, `ONLINE`, `RECONNECTING`, `ERROR` |
| Coordinator | `UNKNOWN`, `CONNECTING`, `ONLINE`, `DEGRADED`, `AUTH_FAILED`, `INCOMPATIBLE`, `OFFLINE` |

Overall state is derived from data-plane truth. A degraded Coordinator does not
override `ONLINE` when Minecraft and Relay are healthy. Conversely, a live
`frpc` PID is insufficient for Relay `ONLINE`.

Relay `ONLINE` requires all of the following within their TTL:

1. the managed `frpc` process is alive;
2. `frpc` reported a successful connection to `frps`;
3. the local Minecraft port accepts a connection;
4. the VPS public Minecraft endpoint accepts a connection;
5. the latest observations have not expired.

## Agent orchestration

The start operation is asynchronous and idempotent:

1. validate the imported server directory, EULA, Java, and configuration;
2. start Minecraft and wait for `READY`;
3. fetch `/v1/info` and validate protocol version;
4. generate an ephemeral `frpc` configuration outside persisted user config;
5. start one managed `frpc` and wait for its successful `frps` connection;
6. probe the public endpoint and publish Relay `ONLINE`.

The stop operation first marks the runtime `STOPPING`, gracefully stops `frpc`,
then stops Minecraft. A future safe-sync hook is intentionally placed after
Minecraft has stopped and before the operation completes; v0.4 does not upload
or download archives.

Duplicate start/stop requests join or return the active operation. Relay never
starts before Minecraft is `READY`. A Minecraft exit immediately invalidates
Relay health and stops the managed relay.

## RelayManager contract

Relay management is isolated behind:

```go
Start(ctx, config) error
Stop(ctx) error
Status() Status
Reconcile(ctx, desiredState) error
Events() <-chan Event
Diagnose(ctx) Diagnosis
```

Process creation, local port probing, public endpoint probing, time, and retry
waiting are injected dependencies. Production uses `os/exec` and TCP probes;
tests use fakes and never require a real Minecraft server or `frps`.

Only one managed process may exist. The manager stores minimal ownership
metadata (PID, executable/config fingerprint, desired state) and validates it
before recovery. It never imports v0.3 `session_id`, `relay_state`, heartbeat,
lease, tunnel, or current-host runtime state.

Retry delays are `1s, 2s, 5s, 10s, 30s`, then remain at `30s`. A stable five
minute run resets the failure count. Network and temporary reachability errors
retry; authentication, invalid configuration, incompatible protocol, and
remote-port conflict errors are terminal until configuration changes. Output
is parsed into bounded structured events, with secrets redacted before storage.

## Configuration and secret handling

Persisted local configuration accepts only:

- `coordinator_host`;
- `coordinator_port` (default `6121`);
- `access_token`.
- `minecraft_local_port` (default `25565`);
- `public_minecraft_port` (default `25565`).

The imported Minecraft directory is recorded by the import action, separate
from the configuration update schema. The FRP server control port comes from
Coordinator `/v1/info`; the local and public Minecraft ports are written
manually and are locked while hosting. The Agent never reads, parses, or writes
`server.properties` and never scans for a likely Minecraft port. Runtime fields such as session, relay,
heartbeat, endpoint, host, lease, and tunnel state are rejected.

The single access token may be stored as plaintext for Hobby Edition, but the
complete value must never appear in logs, events, API responses, or diagnostics.
The local server binds exactly to `127.0.0.1` by default, never `0.0.0.0`.

## HTTP contracts

The Agent serves:

- `GET /local/v1/status`
- `PUT /local/v1/config`
- `POST /local/v1/import`
- `POST /local/v1/start`
- `POST /local/v1/stop`
- `GET /local/v1/operations/{id}`
- `GET /local/v1/events`
- `GET /local/v1/diagnostics`
- `GET /local/v1/logs`

Start and stop return an `operation_id` immediately. Status and diagnostics are
snapshots; event and log responses are bounded. The embedded UI polls status,
shows only player-facing state on its main page, and exposes settings and
diagnostics as secondary panels.

The Coordinator adds the Hobby Edition contract:

- `GET /v1/info`: protocol/server version, FRP server port, public Minecraft
  port, and heartbeat interval;
- `POST /v1/heartbeat`: shared-token authentication, automatic node upsert,
  component status report, and Coordinator status response;
- `GET /v1/status` and `GET /v1/nodes`.

Protocol mismatch is explicit and terminal for the current configuration. These
routes do not create a player tunnel and do not depend on the legacy WebSocket
relay manager.

## Reuse and legacy isolation

Reviewed v0.2 code may be reused narrowly:

- `internal/mcserver`: process ownership and graceful stdin stop;
- `internal/agentconfig`: atomic JSON configuration patterns;
- `internal/coordinator`: HTTP client conventions;
- `internal/localcontrol`: loopback HTTP server patterns.

Each reused module must be adapted to the new state and secret rules and covered
by new tests. `internal/relay`, `internal/playerproxy`, election/takeover flows,
artifact synchronization, and their runtime state remain in history but are
not called by the v0.4 Agent entry path. No old hotfix is bulk cherry-picked.

## Diagnostics and logging

State transitions use a stable event schema: event, component, from, to,
reason, operation ID, and time. At least 500 recent transitions are retained.
Production logs rotate at 20 MiB per file with five files. Diagnostics include
version/OS, Coordinator and protocol observations, Java and EULA checks,
Minecraft and `frpc` process details, local/public probes, recent errors and
transitions, and disk space. All serialization passes through token redaction.

## Acceptance boundary

Automated tests cover singleton process ownership, retry/terminal failures,
stale observations, Minecraft/Relay ordering, aggregate state, API write
rejection, redaction, restart recovery, and idempotent start/stop. Real VPS,
Minecraft, Windows service, Linux service, temporary network loss, browser
closure, Coordinator restart, 24-hour soak, and seven-day acceptance remain
documented manual validation steps.
